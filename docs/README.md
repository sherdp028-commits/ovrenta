## Главные решения

1. **Канал — адаптер, логика — общая.** Telegram и VK переводят события в один формат.
   Запись, ИИ и уведомления не знают о канале.
2. **Вебхук только принимает.** Проверка секрета → сохранение в `inbound_events` с
   уникальным ключом → очередь Celery → `200`. Повторы отбрасываются, перезапуск не
   теряет сообщения.
3. **Двойная запись невозможна на уровне PostgreSQL** — exclusion constraint по
   мастеру и интервалу времени. Проверено на PostgreSQL 16: из 20 одновременных
   попыток проходит одна.
4. **ИИ не выполняет действия сам.** Запись, отмена и перенос — только предложение,
   выполняет backend после подтверждения клиента.
5. **ИИ видит только текущего клиента.** У инструментов нет `client_id`.
6. **Синхронный backend** (SQLAlchemy 2 + psycopg 3, Celery) — проще при нагрузке
   одного салона.

## Отличия от ТЗ (структуру ТЗ разрешено корректировать)

| Что | Почему |
|---|---|
| Порядок этапов: Telegram → ИИ → уведомления → панель → VK | Решение заказчика «сначала Telegram» |
| Нет `telegram_id`/`vk_id` в `clients`, только `client_channels` | Один факт — одно место хранения |
| Новые таблицы `auth_sessions`, `client_consents`, `inbound_events`, `pending_actions`, `campaigns` | Refresh-токены, журнал согласий (152-ФЗ), дедупликация вебхуков, подтверждение действий, подтверждение рассылок |
| `master_services` с `price_override` и `duration_override` | У разных мастеров разные цены и длительность |
| Нет статуса диалога `closed` | Диалог в мессенджере не заканчивается; «закрыть» = вернуть боту |
| Инструменты `propose_*` вместо `create/cancel/reschedule_*` и `confirm_pending_action` | Согласие клиента обеспечивает код, а не только промпт |
| Сценарии на кнопках без ИИ (`/booking`, `/cancel`) | Проверка Telegram до ИИ и запасной режим при сбое LLM |
