# План реализации

Порядок изменён по сравнению с разделом 15 ТЗ по решению заказчика: **сначала
Telegram**. Цепочка «Telegram → запись → ИИ → уведомления → панель» доводится до
рабочего состояния, ВКонтакте подключается после. Каждый этап заканчивается
прогоном тестов и отчётом в формате раздела 17 ТЗ; следующий этап начинается только
после приёмки текущего.

| Этап | Название | Соответствие ТЗ | Нужно решение заказчика |
|---|---|---|---|
| 0 | Проектирование | раздел 18 | — (этот документ) |
| 1 | Каркас проекта | этап 1 | — |
| 2 | БД, бизнес-логика, Admin API | этап 2 + часть этапа 6 (API) | — |
| 3 | Telegram без ИИ | этап 3 | тестовый бот, сервер с доменом |
| 4 | ИИ-администратор | этап 5 | LLM-провайдер (риск R1) |
| 5 | Уведомления | этап 7 | тексты уведомлений |
| 6 | Панель управления | этап 6 | — |
| 7 | ВКонтакте | этап 4 | тестовое сообщество |
| 8 | Возврат клиентов и аналитика | раздел 12 | шаблоны предложений |
| 9 | Тестирование и защита | этап 8 | — |

## Этап 1. Каркас проекта

**Задачи**
- Структура `backend/`, `frontend/` (пустой Next.js-проект), `infrastructure/`, `docs/`
  по [architecture.md](architecture.md#7-структура-проекта); удаление прототипа VK-бота
  из корня (остаётся в истории git).
- FastAPI-приложение: настройки (Pydantic Settings), логирование в JSON с фильтром
  секретов, единый формат ошибок, `/health`, `/ready`.
- SQLAlchemy 2 (psycopg 3), Alembic с пустой первой ревизией, Redis, Celery
  (worker + beat) с тестовой задачей.
- `docker-compose.yml`: postgres 16, redis 7, api, worker, beat; `.env.example`.
- Pytest: фикстуры с настоящим PostgreSQL (отдельная тестовая БД, транзакция на тест).
- Зафиксированные версии зависимостей (`requirements.in` → `requirements.txt`).
- CI (GitHub Actions): линтер (ruff), проверка типов (mypy в мягком режиме), тесты.

**Готово, когда:** `docker compose up` поднимает все сервисы, `/ready` отвечает `200`,
задача Celery выполняется, `pytest` и CI проходят.

## Этап 2. База данных, бизнес-логика, Admin API

**Задачи**
- Модели и миграции всех таблиц из [database.md](database.md), кроме рассылок
  (этап 8); exclusion constraint, составные внешние ключи, индексы.
- Репозитории с обязательным `salon_id`.
- Сервисы: клиенты, мастера, услуги, графики и исключения, расчёт свободных слотов,
  запись / перенос / отмена / завершение / неявка с журналом `audit_logs`.
- Авторизация: вход, refresh с ротацией, выход, лимит попыток входа, роли и права.
- Admin API разделов 3–10 [api.md](api.md) (кроме диалогов — этап 3, и аналитики —
  этап 6) со Swagger.
- Команда `python -m app.cli create-salon` — салон и владелец без панели.

**Тесты (unit + integration):** создание клиента, услуги, мастера; расчёт слотов
(график, перерыв, исключения, буфер, минимальный срок, горизонт, «любой мастер»,
часовые пояса); конфликты и `409`; отмена и перенос; переходы статусов; права ролей;
изоляция салонов (сотрудник салона А не видит данные салона Б); параллельная
запись на одно время (≥ 20 потоков → ровно 1 успешная).

**Готово, когда:** через Swagger можно завести салон, услуги, мастеров, графики и
записать клиента; двойная запись невозможна; все тесты зелёные.

## Этап 3. Telegram (без ИИ)

**Задачи**
- Слой каналов: `InboundMessage`, `OutboundMessage`, `Keyboard`, Channel Gateway с
  повторами и лимитом частоты.
- Адаптер Telegram: клиент Bot API на `httpx`, разбор `message` и `callback_query`,
  отправка, клавиатуры, `request_contact`, «печатает…», обработка ошибок.
- Подключение бота через API (`getMe`, `setWebhook` с секретом, `setMyCommands`).
- Вебхук: секрет, `inbound_events`, дедупликация `update_id`, очередь, восстановление
  зависших событий.
- Conversation Manager: клиент и диалог по внешнему ID, сохранение сообщений,
  блокировка диалога, склейка сообщений подряд, режимы бот/оператор.
- Детерминированные сценарии: `/start`, `/services`, `/booking` (запись на кнопках),
  `/cancel`, `/help`, `/admin`; согласие на обработку ПДн и телефон перед первой
  записью; `pending_actions` и подтверждение.
- Свободный текст на этом этапе: бот отвечает, что поможет кнопками, и предлагает
  «Записаться» / «Позвать администратора». Это рабочий запасной режим, который
  останется и после этапа 4 на случай недоступности LLM.
- API диалогов (раздел 9 [api.md](api.md)): список, сообщения, ответ сотрудника,
  назначение, завершение передачи.

**Тесты:** вебхук (неверный секрет → `403`, повтор `update_id` не обрабатывается
дважды, ответ < 200 мс); разбор событий Telegram на записанных примерах JSON; запись
через кнопки от начала до конца с подменённым Telegram API; подтверждение дважды
(второе нажатие не создаёт запись); ответ сотрудника доходит до клиента; ошибки
`429`/`403` обрабатываются; проверка на реальном тестовом боте на сервере.

**Готово, когда:** клиент в Telegram видит услуги, записывается, отменяет запись;
сотрудник видит переписку через API и может ответить.

**Нужно от заказчика:** тестовый бот (токен от @BotFather) и сервер с доменом и HTTPS
для вебхука (или временный туннель для разработки).

## Этап 4. ИИ-администратор

**Задачи**
- Решение по LLM-провайдеру (R1) → адаптер(ы) в `app/integrations/llm/`.
- `LLMProvider` (4 метода из ТЗ), оркестратор с лимитами, инструменты с Pydantic-схемами,
  системный промпт из настроек салона, динамический контекст и краткое содержание
  длинной истории.
- `request_human_operator`, оповещения сотрудникам, режим `waiting_operator`.
- `classify_intent` для аналитики конверсии; `ai_usage_logs`; дневной бюджет.

**Тесты:** оркестратор на `FakeProvider` (валидация, привязка к клиенту, подтверждения,
лимиты, запасные ответы); 12 сценариев раздела 14.3 ТЗ на реальной модели × 3 прогона;
сравнение моделей и `effort` по качеству и стоимости.

**Готово, когда:** все 12 сценариев проходят во всех прогонах; запись без
подтверждения невозможна; чужие данные не раскрываются; стоимость хода измерена.

## Этап 5. Уведомления

**Задачи:** Celery beat; подтверждение, напоминания за 24 ч и 2 ч, отмена, перенос,
предложение освободившегося времени (клиентам, которые искали это время и не нашли —
по их согласию); настройки и шаблоны по типам; `dedupe_key`; повторы при временных
ошибках; учёт часового пояса, статуса записи, согласия и доступности канала.

**Тесты:** планирование при создании, переносе и отмене; повторный запуск
планировщика не создаёт дублей; отменённая запись не получает напоминание; временная
ошибка → повтор, постоянная → `failed`; перезапуск worker'а посреди отправки.

## Этап 6. Панель управления

**Задачи:** Next.js + TypeScript + Tailwind, адаптивная вёрстка (мобильные — обязательно):
вход; главная; расписание (день / неделя / мастер); клиенты и карточка; услуги;
мастера и графики; диалоги с ответом, назначением и завершением передачи; настройки
салона, бота, уведомлений и каналов (подключение Telegram по токену). Аналитика
`overview`, `appointments`, `clients`, `conversion`.

**Тесты:** компонентные тесты ключевых форм; e2e (Playwright) — вход, создание услуги,
мастера и графика, запись из панели, ответ в диалоге; проверка на ширине 375 px.

## Этап 7. ВКонтакте

**Задачи:** сверка с документацией VK (пункты «⚠ проверить»); адаптер VK: Callback API
(confirmation, `secret`, `ok`), `message_new`, `message_event`, `messages.send` с
детерминированным `random_id`, клавиатуры; подключение сообщества из панели.

**Тесты:** вебхук VK (confirmation, неверный секрет, повтор `event_id`); запись на
кнопках и через ИИ — те же сценарии, что в Telegram, на подменённом VK API; проверка на
реальном тестовом сообществе.

## Этап 8. Возврат клиентов и аналитика

**Задачи:** сегменты (новые, постоянные, не были 30/60/90 дней); рассылка из шаблона
с предпросмотром; подтверждение владельцем; отправка только клиентам с согласием и
доступным каналом, ссылка на отписку, лимит частоты; `campaign_logs`.

**Тесты:** сегменты на подготовленных данных; рассылка без подтверждения не уходит;
клиент без согласия не получает; повторный запуск не дублирует отправку.

## Этап 9. Тестирование и защита

Нагрузочные тесты (одновременные клиенты, параллельные записи, повторы вебхуков,
перезапуск, недоступность LLM и Telegram/VK); проверка безопасности (права и изоляция
по всем эндпоинтам, лимиты, заголовки, секреты в логах, зависимости — `pip-audit`,
`npm audit`); резервное копирование и восстановление. Подробно — [testing.md](testing.md).

## Этап 10. Первый запуск

Сервер, домен, HTTPS, развёртывание по [deployment.md](deployment.md); подключение
Telegram и VK реального салона; заполнение услуг, мастеров и графиков; юридическая
проверка (R1); пилот с салоном 1–2 недели с ежедневным разбором диалогов.
