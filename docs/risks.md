# Риски и технические ограничения

Оценки: В — вероятность, Вл — влияние (Н — низкое, С — среднее, В — высокое).

## 1. Ключевой риск: LLM-провайдер и персональные данные (R1)

**Суть.** Целевые клиенты продукта — салоны в России. Сходятся три требования:

1. **Доступность провайдера.** Anthropic (Claude) не обслуживает Россию: её нет в
   списке поддерживаемых стран (anthropic.com/supported-countries, проверено
   2026-11-02; Беларуси тоже нет, Казахстан, Армения и Грузия есть). Работа с API из
   неподдерживаемой страны нарушает условия провайдера. Обходить это ограничение
   мы не будем.
2. **Локализация ПДн (152-ФЗ).** Запись, накопление и хранение персональных данных
   граждан РФ должны вестись в базах данных на территории РФ. Значит, PostgreSQL
   салона из России — на сервере в России.
3. **Трансграничная передача.** Текст переписки с именем клиента, отправленный
   зарубежному LLM-провайдеру, — это передача ПДн за рубеж. Для неё нужны уведомление
   Роскомнадзора и оценка страны получателя. Кроме того, согласие на обработку ПДн,
   по известным мне изменениям закона, должно оформляться отдельным документом
   (⚠ проверить у юриста).

**Варианты:**

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| А. Российский LLM-провайдер (например, YandexGPT или GigaChat) | БД и сервер в РФ, LLM в РФ | Нет трансграничной передачи, провайдер доступен | Нужно проверить качество вызова инструментов на наших 12 сценариях; адаптер под их API |
| Б. Claude для салонов вне РФ | Сервер и юрлицо в поддерживаемой стране (например, Казахстан, Армения, Грузия) | Сильный вызов инструментов | Не подходит для салонов в России; свои законы о данных в каждой стране |
| В. Обе ветки | Адаптеры А и Б, выбор в конфигурации установки | Продукт для разных рынков | Двойные ИИ-тесты и сопровождение |

**Рекомендация.** Решить до этапа 4, где будут работать салоны первых клиентов.
Если в России — делаем вариант А: на этапе 4 первым пишется адаптер российского
провайдера, а на этапе проектирования перед этим проверяется его поддержка вызова
функций (по моим данным, у обоих названных провайдеров она есть, но детали API и
качество надо проверить). Этапы 1–3 от выбора не зависят. Юридическую схему
(оператор ПДн, хостинг, договор с LLM-провайдером, тексты согласий) проверяет юрист до
запуска с реальным салоном, как и требует раздел 13 ТЗ.

**Меры в архитектуре в любом случае:** в LLM не уходят телефон, заметки и данные
других клиентов; провайдер меняется конфигурацией; журнал `ai_usage_logs` не хранит
полные тексты запросов.

## 3. Технические ограничения MVP (осознанные)

1. **Ресурсы не моделируются.** Пересекаться не могут только записи одного мастера.
   Если в салоне два мастера делят одно кресло или аппарат, система это не учтёт.
2. **Один перерыв в день** у мастера. Сложные графики — через исключения на дату.
3. **Одна услуга в записи.** «Маникюр + педикюр» — две записи подряд (ИИ может
   предложить их последовательно).
4. **Длительность фиксирована** для пары «мастер–услуга», без вариантов («длинные
   волосы +30 минут»). Варианты оформляются отдельными услугами.
5. **Без онлайн-оплаты и предоплаты.**
6. **Без групповых чатов** в Telegram и VK.
7. **Ответы сотрудника — из панели**, а не из Telegram.
8. **Панель обновляется опросом** раз в 5–10 секунд, без WebSocket.
9. **Объединение клиентов** из разных каналов — автоматически только по подтверждённому
   телефону; ручное объединение — после MVP.
10. **Один язык** — русский.
