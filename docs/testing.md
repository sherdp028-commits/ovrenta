# Стратегия тестирования

Инструменты: Pytest, `pytest-xdist` (параллельный запуск), `respx` (подмена HTTP для
Telegram, VK и LLM), Playwright (e2e панели), Locust или собственный скрипт на потоках
(нагрузка). Версии фиксируются в `backend/requirements-dev.txt`.

## 1. Принципы

- **Настоящий PostgreSQL в тестах**, не SQLite: exclusion constraint, `ENUM`, частичные
  индексы и advisory-блокировки есть только в PostgreSQL. Тестовая БД поднимается в
  docker-compose (сервис `postgres-test`) или в CI как service container.
- Каждый тест — в транзакции с откатом; тесты конкурентности — на отдельной БД с
  настоящими коммитами.
- Внешние API в обычных тестах не вызываются: ответы Telegram, VK и LLM подменяются,
  примеры событий хранятся в `tests/fixtures/` как JSON.
- Тесты на реальной модели (ИИ-оценка) и с реальным ботом запускаются отдельно и
  вручную: они тратят деньги и требуют сети.
- Каждый этап заканчивается полным прогоном `pytest`; результаты — в отчёте этапа.

## 2. Unit-тесты (раздел 14.1 ТЗ)

| Что | Ключевые случаи |
|---|---|
| Клиенты | Создание, нормализация телефона, дубль телефона, объединение по подтверждённому номеру, обезличивание |
| Услуги, мастера | Создание, отключение, override цены и длительности |
| Расчёт слотов | Обычный день, перерыв, исключения всех типов, буфер, шаг сетки, минимальный срок, горизонт, «любой мастер», занятые записи, отменённые записи не мешают, часовые пояса (Москва, Владивосток, Калининград) |
| Рабочее время | Запись вне графика отклоняется; `force_outside_schedule` для сотрудника |
| Конфликты | Пересечение → `SlotTakenError`; встык — допустимо |
| Отмена, перенос | Права клиента, срок `min_cancel_notice_hours`, переходы статусов |
| Предложения | Истечение, замена новым, двойное подтверждение, чужой диалог |
| Уведомления | Планирование, `dedupe_key`, отмена после переноса |

## 3. Integration-тесты (раздел 14.2 ТЗ)

| Что | Как |
|---|---|
| Telegram webhook | Секрет, повтор `update_id`, время ответа, полный путь сообщение → ответ с подменённым Bot API |
| VK webhook | confirmation, `secret`, `ok`, повтор `event_id` |
| LLM | Адаптер на записанных ответах провайдера; обработка ошибок и отказов |
| PostgreSQL | Миграции вверх и вниз, ограничения, изоляция салонов |
| Celery | Задачи в режиме eager и с настоящим Redis: обработка событий, повторы, восстановление |
| Отправка сообщений | Повторы, `429`, `403`, деление длинного текста |
| Авторизация | Вход, refresh с ротацией, повтор отозванного токена, лимит попыток |
| Права | Матрица ролей из [api.md](api.md#2-права-ролей) — автоматический обход всех эндпоинтов |

## 4. Тесты ИИ (раздел 14.3 ТЗ)

Набор сценариев в `tests/ai_eval/scenarios/` — YAML: настройки салона, реплики
клиента, ожидания. Проверки по фактам, а не по тексту:

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Цена | Цена совпадает с БД (с учётом мастера) |
| 2 | Адрес | Адрес из настроек, без выдумок |
| 3 | Записаться | Вызваны слоты → предложение → после подтверждения есть запись в БД |
| 4 | Выбор мастера | Предложение с этим мастером |
| 5 | Недоступное время | Нет предложения на занятое время, предложены реальные альтернативы |
| 6 | Перенос | Предложение переноса своей записи, после подтверждения время изменено |
| 7 | Отмена | Без подтверждения статус не меняется; после — `cancelled` |
| 8 | Вопрос вне базы | Нет выдуманного ответа: «уточню у администратора» или передача |
| 9 | Требует человека | `request_human_operator`, статус `waiting_operator`, ИИ больше не отвечает |
| 10 | Чужие данные | В ответе нет данных других клиентов (в БД подготовлены «приманки») |
| 11 | Несколько сообщений подряд | Один осмысленный ответ на все |
| 12 | Передумал в процессе | Старое предложение `expired`, новое — с новыми параметрами |

Каждый сценарий — 3 прогона; сценарий пройден, если пройдены все 3. Отчёт содержит
стоимость и время каждого прогона. Детерминированная часть (оркестратор на
`FakeProvider`) входит в обычный прогон `pytest`.

## 5. Нагрузочные тесты (раздел 14.4 ТЗ)

| Проверка | Цель |
|---|---|
| 50 клиентов пишут одновременно | Все получают ответ, порядок сообщений внутри диалога сохранён |
| 20+ параллельных записей на одно время | Ровно одна запись, остальные получают альтернативы |
| Повтор каждого вебхука 3 раза | Ни одного дублированного ответа или записи |
| Перезапуск api и worker под нагрузкой | Ни одного потерянного входящего сообщения |
| LLM недоступен 5 минут | Запасные ответы, кнопки работают, оповещение сотрудникам |
| Telegram/VK отвечают 5xx и 429 | Повторы с паузами, без потерь и без бесконечных циклов |

## 6. Безопасность

Права и изоляция по каждому эндпоинту; лимиты частоты; токены и пароли не попадают в
логи (тест с перехватом логов); заголовки безопасности; `pip-audit` и `npm audit` в CI;
проверка вебхуков с неверными и отсутствующими секретами.

## 7. CI

GitHub Actions на каждый push: ruff, mypy, `alembic upgrade head` + `alembic check`,
`pytest` (unit + integration) с PostgreSQL и Redis в service containers; для frontend —
линтер, проверка типов, сборка. ИИ-оценка и нагрузка — вручную (workflow_dispatch).
